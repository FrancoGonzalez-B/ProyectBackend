ICINF1108 · Desarrollo de Backend

API backend
para una tienda de ropa

Catálogo, variantes de inventario, clientes y pedidos con persistencia en MySQL.

Equipo: completar nombres antes de la defensa.

1 · Problema y usuarios

Información de tienda dispersa

  • Administradores necesitan mantener catálogo, tallas y stock coordinados.
  • Clientes necesitan consultar productos y hacer seguimiento de sus pedidos.
  • Un stock desactualizado provoca ventas sin disponibilidad y pedidos inconsistentes.

1 · Alcance y aceptación

API REST, sin frontend

  • Registrar, consultar, modificar y eliminar categorías, productos y clientes.
  • Administrar variantes, autenticación, pedidos y estados.
  • Fuera de alcance: pago real, despacho y aplicación frontend.
  • Aceptación: CRUD, validaciones, inventario transaccional y datos tras reiniciar.

2 · Dominio y relaciones

Entidades y relaciones persistentes

Categoría 1 → N Producto 1 → N Variante
Cliente 1 → N Pedido 1 → N Detalle
Variante 1 → N Detalle

Diagrama de clases y esquema relacional: docs/modelo-y-arquitectura.md.

2 · Reglas de negocio

Inventario seguro por variante

  • La variante (talla/color) es la fuente de stock; el total del producto se sincroniza.
  • Precio y total del pedido se calculan desde la base de datos.
  • Pedido, detalle y descuento se confirman juntos en una transacción.
  • Cancelar un pedido pendiente devuelve stock una sola vez.

3 · REST y OpenAPI

32 operaciones documentadas

  • Swagger UI: /api-docs/; especificación: /openapi.json.
  • Catálogo público; operaciones administrativas protegidas por rol.
  • Errores uniformes con código, mensaje y detalles.
  • La colección Postman prueba CRUD, filtros, entradas inválidas y recursos inexistentes.

3 · Arquitectura

Recorrido de una solicitud

HTTP → ruta/DTO → controlador → servicio
→ repositorio Sequelize → modelo ORM → MySQL

Ejemplo: POST /pedidos valida permisos y persiste pedido e inventario en una transacción.

3 · Persistencia

Migraciones y datos reproducibles

  • MySQL/MariaDB se accede mediante Sequelize.
  • Migraciones versionadas preparan tablas y restricciones.
  • Seeders idempotentes: categorías, productos, variantes, dos clientes, dos pedidos y dos detalles.
  • Base local aislada para pruebas: tiendatest_local.

4 · Demostración y evidencia

Comprobaciones ejecutadas

  • 24/24 pruebas unitarias/de contrato y 21/21 de integración MySQL.
  • Persistencia comprobada leyendo una categoría tras reiniciar la API.
  • Errores demostrados: DTO 422, recurso 404 y transición inválida 409.
  • Verificación de integridad sin inconsistencias.

5 · Decisiones y mejoras

Decisiones, limitaciones y próximos pasos

  • Transacciones y bloqueo de inventario evitan vender unidades inexistentes.
  • Limitación actual: no se integra una pasarela de pago ni despacho real.
  • Mejoras futuras: pagos, seguimiento logístico y alertas de stock.
  • Todos los integrantes deben poder explicar las capas y la evidencia.
